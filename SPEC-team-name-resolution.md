# Spec: корректный резолв имени клуба (P3-7, часть 1)

Статус: **черновик, ждёт ревью**
Связано: `Project_Audit_Report.md` → P3-7; `CLAUDE.md` → раздел «Domain model»

---

## Objective

`database.resolve_team_name()` приводит любое пользовательское/OCR-имя клуба к каноническому.
Сейчас он матчит против 16 имён из `config.KPL_TEAMS` + `TEAM_ALIASES`. При ~80 клубах в
5 дивизионах это **молча теряет данные**: разные клубы схлопываются в один канон, а
`get_standings` ключует аккумулятор этим каноном (`teams[canon]`, [database.py:2230](database.py:2230),
[2306](database.py:2306)) — три клуба дают две строки, тренер исчезает из таблицы.

**Пользователь:** тренер, который сыграл матч и не нашёл себя в таблице; админ, который
проводит результат через OCR-драфт и получает чужой клуб.

**Успех:** ни одно зарегистрированное имя клуба не резолвится в имя другого клуба —
ни при каких входных данных, встречающихся в `users.team_name` живой БД.

### Подтверждённое репро (локально, до фикса)

```
Расинг Сантандер -> Расинг    Расинг Ланс -> Расинг
Спортинг Хихон   -> Порту     ПСЖ         -> ПСВ
```

Корневая причина — два конкретных тира в [database.py:1560-1585](database.py:1560):

| Вход | Тир | Механика |
|---|---|---|
| `Спортинг Хихон` | 4 — подстрока | алиас `порт`→`Порту` является подстрокой `спортинг хихон`; в словаре он раньше `спортинг`, поэтому выигрывает он |
| `Расинг Сантандер` | 4 — подстрока | алиас `расинг` — подстрока входа |
| `Расинг Ланс` | 4 — подстрока | то же (фаззи дал бы 0.706 — тоже выше порога) |
| `ПСЖ` | 5 — фаззи | `SequenceMatcher('псж','псв') = 0.667 ≥ 0.65` |

То есть дефект — не только низкий порог. Тир 4 (`norm in a_norm or a_norm in norm`)
ломает всё многословное вне зависимости от порога, и он срабатывает **раньше** фаззи.

### Зафиксированные решения (из ревью)

| Вопрос | Решение |
|---|---|
| Источник канона | **Расширенный статический список в `config.py`** (не запрос к `users`) |
| Нет уверенного совпадения | **Вернуть вход как есть** + новая `resolve_team_name_ex()` с флагом уверенности |
| Объём | **Резолвер + реестр + тесты.** ~50 вызовов не трогаем — они получают фикс автоматически |
| Проверка | **uuid-фикстуры в тестах + скрипт аудита, прогоняемый на VPS** |

### Один флаг по выбранному источнику

Статический список расходится с БД при регистрации каждого нового клуба, и расхождение
тихое — ровно тот класс бага, который мы чиним. Спека делает две вещи, чтобы это не
повторилось, **не меняя выбранный источник истины**:

1. Список не набивается руками — его **генерирует скрипт аудита из живой БД** (иначе
   нельзя: локальный `league.db` пустой, реальные данные только на VPS).
2. Расхождение делается **громким**: `verify_registry_against_db()` + тест-страж, который
   падает, если в `users.team_name` есть клуб, отсутствующий в реестре.

```
club_registry.py                    → НОВЫЙ. Нормализация, алиасы, реестр, резолв
config.py                                    → ИЗМЕНЕН. + CLUB_REGISTRY (все ~80 клубов)
database.py                                  → ИЗМЕНЕН. Тонкие делегаты, -~130 строк
scripts/audit_team_resolution.py             → НОВЫЙ. Read-only аудит живой БД
tests/test_team_name_resolution.py           → НОВЫЙ. Чистые юнит-тесты резолвера
tests/test_standings_name_collision.py       → НОВЫЙ. Интеграция: uuid-фикстуры + get_standings
```

Почему отдельный модуль, а не правка на месте в `database.py`: `normalize_team_name` и
`TEAM_ALIASES` (~70 строк словаря) — чистый CPU без единого SQL. Держать их в
`database.py` означает, что любой будущий потребитель реестра тянет за собой слой БД и
добавляет звено к 15 циклическим цепочкам из аудита (P4-6). `club_registry` импортирует
**только `config`** — новых циклов не создаёт.

### Совместимость обязательна

`database.py` **реэкспортирует** `normalize_team_name`, `resolve_team_name`, `teams_match`,
`TEAM_ALIASES`. Все существующие `database.resolve_team_name(...)` и
`from database import normalize_team_name` продолжают работать без правок. Это условие
того, что ~50 вызовов не трогаются.

## Code Style

Русские строки — пользователю; английские идентификаторы и докстринги; комментарии — как в
редактируемом файле (`database.py` смешанный). Тиры резолва — явные, пронумерованные,
каждый возвращает результат **только если он однозначен**.

```python
# club_registry.py

class ResolveMethod(str, Enum):
    EXACT = "exact"          # точное совпадение с каноном
    ALIAS = "alias"          # словарь TEAM_ALIASES
    JOINED = "joined"        # склейка токенов: "ривер плейт" -> "риверплейт"
    PREFIX = "prefix"        # единственный кандидат по префиксу
    FUZZY = "fuzzy"          # difflib, только с запасом над вторым кандидатом
    NONE = "none"            # не разрешено — вход возвращается как есть


@dataclass(frozen=True, slots=True)
class TeamResolution:
    """Outcome of resolving a raw team name against the club registry."""
    raw: str
    canonical: str | None      # None when the name could not be resolved confidently
    method: ResolveMethod
    confidence: float          # 1.0 for exact/alias, difflib ratio for fuzzy, 0.0 for none
    candidates: tuple[str, ...]  # non-empty when ambiguous: what it could have been

    @property
    def is_confident(self) -> bool:
        return self.canonical is not None


def resolve_team_name(name: str | None) -> str:
    """Resolve a raw team name to its canonical form, or return it unchanged.

    Backwards-compatible wrapper: never returns an empty string for a non-empty
    input, so existing `resolve_team_name(x) or x` call sites keep working.
    """
    if not name:
        return ""
    res = resolve_team_name_ex(name)
    return res.canonical if res.canonical is not None else str(name).strip()
```

### Алгоритм: тиры по порядку

Первый тир, давший **однозначный** результат, выигрывает. Неоднозначность на любом тире =
остановка со `method=NONE` и заполненным `candidates` — **не** переход к следующему тиру
(иначе более слабый тир «дорешает» то, что более сильный признал спорным).

| # | Тир | Правило | Однозначность |
|---|---|---|---|
| 1 | `EXACT` | `norm(input)` совпал с `norm(canon)` | Гарантирована: `idx_users_team_name_unique` |
| 2 | `ALIAS` | `norm(input)` — ключ `TEAM_ALIASES`, **и** его значение есть в реестре | Алиас, конфликтующий с каноном другого клуба, отбрасывается на старте |
| 3 | `JOINED` | склейка токенов совпала с каноном или алиасом | Как тир 1–2 |
| 4 | `PREFIX` | ровно **один** канон начинается с `norm(input)` | ≥2 кандидатов → `NONE` + candidates. Так `Расинг` при живых «Расинг Сантандер»/«Расинг Ланс» не угадывается |
| 5 | `FUZZY` | `difflib` по реестру + алиасам | Три жёстких предохранителя ниже |

**Предохранители тира 5** (каждый закрывает конкретный подтверждённый кейс):

- `FUZZY_MIN_LEN = 5` — вход короче 5 нормализованных символов фаззи не проходит вообще.
  Убивает `ПСЖ → ПСВ` (0.667) насухо. Цена: опечатки в коротких именах (`АЕК`, `Аякс`)
  ловятся только тирами 1–3, то есть словарём алиасов. Приемлемо: на трёх буквах
  «похожесть» неотличима от «другой клуб».
- `FUZZY_THRESHOLD = 0.87` вместо 0.65.
- `FUZZY_MARGIN = 0.07` — если второй по счёту **другой** канон отстаёт от лучшего меньше
  чем на margin, результат неоднозначен → `NONE`. Это то, чего в текущем коде нет совсем:
  он берёт `best_score` без взгляда на второго.

**Тир «подстрока» удаляется целиком.** Он и есть источник трёх из четырёх репро-кейсов, и
безопасной версии у него нет: `Расинг` — легитимная подстрока `Расинг Ланс` и при этом
самостоятельный клуб. Его работу перенимают тиры 2 (алиасы) и 4 (уникальный префикс).

### `teams_match` — тот же дефект, та же правка

[database.py:1613](database.py:1613) содержит `a_norm in b_norm or b_norm in a_norm` и
словесный матч ниже — оба дают `teams_match("Расинг", "Расинг Ланс") == True`. Защита от
схлопывания на строке 1601 читает `config.CLUBS` (те же 16 имён), поэтому на 80 клубах не
срабатывает. Правка: защита читает **полный реестр**, и если обе стороны — различные
зарегистрированные клубы, возврат `False` **до** подстрочного и словесного тиров.

## Testing Strategy

pytest, файлы в `tests/`, по одному на область. `pytest.ini` даёт `-n auto --dist loadfile`:
файлы идут параллельно против одного `league.db`, поэтому любая фикстура с записью в
`users` получает `uuid4`-суффикс — как в `tests/test_chat_division_scope.py`.

Покрытие у функции сейчас почти нулевое: `resolve_team_name`/`teams_match` встречаются
всего в 2 тестах из 78. Это и есть причина, по которой дефект дожил до 80 клубов.

**Уровень 1 — юнит, без БД** (`tests/test_team_name_resolution.py`):
- Четыре репро-кейса как явные ассерты: каждый резолвится **в себя**, не в чужой клуб.
- По одному тесту на тир: exact, alias, joined, prefix-unique, fuzzy-hit.
- Неоднозначность: `Расинг` при двух «Расинг *» в реестре → `method=NONE`,
  `canonical is None`, `candidates` содержит оба.
- Предохранители: `FUZZY_MIN_LEN` (трёхбуквенный мусор), `FUZZY_MARGIN` (два близких
  кандидата), `FUZZY_THRESHOLD`.
- **Анти-регресс:** все 16 имён `KPL_TEAMS` и **каждый** ключ `TEAM_ALIASES` резолвятся
  ровно в то, во что резолвились до правки. Это ловит поломку OCR-транслита.
- **Инвариант тотальности:** для каждой пары различных канонов реестра
  `resolve_team_name(a) != resolve_team_name(b)`. Параметризованный тест — именно он не
  даст дефекту вернуться при добавлении клуба.
- Реестр подставной (monkeypatch), чтобы тесты не зависели от содержимого `config.py`.

**Уровень 2 — интеграция с БД** (`tests/test_standings_name_collision.py`):
- Сеет дивизион и три клуба с коллизионными именами (`Расинг Сантандер {uuid}`,
  `Расинг Ланс {uuid}`, `Расинг {uuid}`) + подтверждённые матчи между ними.
- Ассерт: `get_standings(division_id=...)` возвращает **три** строки, у каждой свой
  `telegram_id`, суммы очков сходятся. Это прямой тест исчезающего тренера.
- `teams_match` на тех же именах → `False` попарно.

**Уровень 3 — живая БД, вручную на VPS** (`scripts/audit_team_resolution.py`, read-only):
- Читает все `users.team_name`, прогоняет резолв, печатает коллизии (два имени → один
  канон), недостижимые клубы (нет в реестре) и дрейф реестр↔БД.
- Exit code 1 при любой находке — годится для разового прогона и для cron позже.
- `--emit-config` печатает готовый блок `CLUB_REGISTRY` для вставки в `config.py`.
- **Прогон до и после фикса**, вывод обоих — часть приёмки.

## Boundaries

**Always**
- Гонять `python -m pytest tests/ -q` целиком перед коммитом: правка задевает ~50 вызовов.
- Сохранять реэкспорты из `database.py` — иначе эти 50 вызовов ломаются.
- Держать `resolve_team_name` синхронной и без I/O: аудит явно вывел её из-под P1-обёрток
  в `to_thread` (`Project_Audit_Report.md`, «Explicitly out of scope»). Реестр — заранее
  посчитанный индекс в памяти, резолв — LRU-кэш.
- Коммиты по Conventional Commits: `fix(database): ...`.

**Ask first**
- Любое изменение сигнатуры `resolve_team_name` / `teams_match`.
- Правка вызывающих файлов (`handlers/`, `services/graphics/`, `api/`) — по решению о
  объёме они вне спеки.
- Удаление `KPL_TEAMS` / `CLUBS` из `config.py`: на них завязана ветка `get_standings`
  без дивизиона и `teams_match`; это отдельный шаг P3-7.
- Миграции схемы. Реестр статический, схема не трогается — если понадобится, это сигнал,
  что спека разошлась с реальностью.

**Never**
- Класть реальные имена клубов из VPS в тесты как фикстуры: `league.db` — не фикстура, и
  это живые пользовательские данные.
- Удалять или ослаблять существующие тесты, чтобы получить зелёный прогон.
- Ронять `TEAM_ALIASES`: это накопленный словарь OCR-опечаток и транслита, потерять его
  = уронить распознавание скриншотов.
- Подключать резолвер к БД внутри горячего цикла `get_standings`.

## Success Criteria

1. Все четыре репро-кейса резолвятся в себя:
   ```bash
   python -c "import database as d; print([d.resolve_team_name(x) for x in ['Расинг Сантандер','Расинг Ланс','Спортинг Хихон','ПСЖ']])"
   ```
   → `['Расинг Сантандер', 'Расинг Ланс', 'Спортинг Хихон', 'ПСЖ']`
2. Инвариант тотальности зелёный: для любых двух различных канонов реестра резолв даёт
   различные результаты.
3. `get_standings` на дивизионе с тремя коллизионными клубами возвращает **три** строки.
4. `teams_match("Расинг", "Расинг Ланс") is False`.
5. Все 16 `KPL_TEAMS` и каждый ключ `TEAM_ALIASES` резолвятся как до правки.
6. `python -m pytest tests/ -q` — без новых падений относительно текущего baseline
   (baseline фиксируется первым шагом реализации).
7. `scripts/audit_team_resolution.py` на VPS: 0 коллизий, 0 недостижимых клубов,
   выход 0. Вывод до/после приложен к результату.
8. Ни один файл вне `config.py`, `database.py`, `club_registry.py`, `scripts/`,
   `tests/` не изменён.

## Open Questions

1. **Список клубов.** Реестр генерируется `--emit-config` на VPS, но кто-то должен его
   там прогнать и отдать вывод — локально данных нет. До этого реализация идёт на
   синтетическом реестре в тестах, а `config.CLUB_REGISTRY` остаётся с 16 именами и
   пометкой TODO. Прогоните скрипт и пришлите вывод — я вставлю.
2. **`Расинг` как самостоятельный клуб.** В `KPL_TEAMS` он есть. Если в живой БД он
   зарегистрирован именно так, тир 1 отдаст его себе, и всё сходится. Если же реального
   клуба «Расинг» нет и это наследие КПЛ, то одинокий `Расинг` из OCR станет
   неоднозначным (тир 4, два кандидата) и вернётся как есть — драфт покажет админу сырое
   имя. Подтвердите, что это приемлемое поведение для OCR-потока.
3. **Порог 0.87 / margin 0.07.** Цифры выбраны так, чтобы пройти подтверждённые кейсы
   (`псж/псв` 0.667, `спортинг хихон/спортинг` 0.727, `расинг ланс/расинг` 0.706 — все
   отсекаются). На реальных 80 именах их нужно перепроверить прогоном скрипта; если
   всплывут ложные отрицания на OCR-опечатках, правильная реакция — **добавить алиас**,
   а не снижать порог.
4. **Ambiguity в OCR-драфте.** `resolve_team_name_ex` даёт `candidates`, но подключение
   их к UI драфта (спросить админа вместо тихого проглатывания) — вне объёма. Отдельной
   карточкой?
